# Parallel execution

For substantial work, define a bounded work breakdown before execution. Each task identifies its intended outcome, observable acceptance criteria, dependencies, exclusive write paths and other shared resources, and Executor complexity. Decompose until independent useful work can proceed concurrently; do not create artificial fragments, duplicate work, or discard valid completed checks. Consult the appropriate Advisor before finalizing the plan or a material replan.

Every substantive phase, including Low-complexity implementation, tests, research, documentation, release preparation and rework, needs an actual bounded Executor owner. Advisor consultation is not delegated execution. Before starting, show the host assignment ID or a concrete blocker/permitted exception; planned briefs and reservations do not establish dispatch. Repeat at material phase changes, resume, late correction and before acceptance. The root may coordinate, inspect sources, run existing checks for independent verification, accept work, coordinate integration and complete authorized publication; it must not author substantive deliverables under those labels. The Orchestrator owns the plan and independently reviews each result and its evidence. A dependency is satisfied only when the Orchestrator accepts the corresponding result. A candidate marked complete, an agent's self-reported pass, or a pending review is not acceptance. Reopened work and required rework block dependent tasks until independently accepted again.

The root owns outcomes, the work breakdown, acceptance and ledger. Assign each bounded stage one execution owner: native or direct. Represent an opaque native subtree as one WBS stage; the native runtime may schedule its internal steps freely, and root acceptance of its result unlocks downstream work. Treat native stages individually as controlled only where real return, acceptance and resume boundaries exist. Do not mirror the subtree with direct assignments.

At each scheduling opportunity, form a maximal feasible ready set in plan order using only verified capacity: dependencies must be accepted, capacity available, and ownership and exclusive resources compatible with running and selected tasks. Unknown native occupancy remains unknown, not zero; do not claim maximal utilization or launch competing direct fan-out unless disjoint capacity is independently verified. Use all available useful slots; do not impose an arbitrary worker cap. Count every live helper against host capacity, including Advisors, reviewers, and rework, as well as Executors. A feasible greedy ready set is sufficient; this policy does not require a maximum-cardinality solver. Shared writes, deployments, and other exclusive resources must remain serialized.

Dispatch continuously. Recompute after accepted completion, launch failure, settled cancellation, or resource release. Start an eligible successor immediately even while unrelated slow work continues. Fill available capacity with independent ready work while reviews are pending. Respect actual host limits and user authorization; do not fabricate launch or completion records.

The host performs scheduling and native launches. The optional `scripts/work_breakdown.py` pure helper validates a snapshot through `readiness(plan, accepted, running, capacity, other_inflight=None, *, enabled=None)` and returns `ready`, `status`, and `used_capacity`. The caller must supply an independently verified nonnegative count of occupied slots outside `running`; omitted or unknown occupancy raises `ValueError`, and zero is valid only when verified. The helper does not detect occupancy. Plan tasks have `id`, `outcome`, `acceptance`, `dependencies`, `complexity` (`low`, `medium`, or `high`), `write_paths`, and `resources`. Status identifies each task's readiness or blocker; used capacity includes running tasks, other in-flight helpers, and selected ready tasks. Invalid or inconsistent snapshots raise `ValueError`. Write paths use lexical POSIX normalization, so the host must also account for actual filesystem aliases and other resource conflicts. Its greedy plan-order result describes a feasible snapshot, not an actual batch launch; it does not launch helpers, persist state, or replace independent acceptance. Recompute from current facts before acting.

For execution checkpoints, add optional task `execution` metadata and supply an explicit boolean `enabled` from current session status; legacy snapshots without execution metadata keep their existing behavior. Required metadata fields are `activity` and `proposed_owner`; optional fields are `assignment`, `root_started`, `root_start_authorized`, `user_exception`, and `dispatch_blocker`. Activities distinguish substantive `code`, `test_authoring`, `test_work`, `research`, `documentation`, `release_preparation`, and `semantic_integration` from root `coordination`, `source_inspection`, `independent_verification`, and `acceptance`. Describe the actual work, not a convenient label.

A returned host assignment is represented as `{"assignment_id":"ACTUAL_HOST_ID","role":"executor","stage":"execution","host_returned":true}`; an Advisor planning/design assignment does not satisfy Executor ownership. This remains a declared host snapshot, not provider authentication: compare it with the real returned host result. An exception requires concrete instruction `evidence`, `scope` equal to the exact task ID, and `authority` of `new_explicit_user_instruction` or `higher_priority_governing_instruction`; a capacity/receipt limitation is not an exception. The result adds `execution_checkpoints` per task with `execution_allowed`, `next_action`, `ownership_basis`, `provider_verified: false`, `learning_eligible: false`, `deviation`, `root_start_authorized`, and `preserve_existing_work`. With policy off, it returns `defer_to_host_policy`, never blanket root permission.

Keep current permission separate from authorization when earlier root work began. If `root_started: true`, optional `root_start_authorized` accepts exactly `true`, `false`, or `null`: true declares that root work was authorized when it began, false declares it was unauthorized, and omitted/null means unknown. This is a host-declared historical fact, not provider verification; do not infer it from the current owner, current mode, a new exception, or free-text explanation. For substantive work already started, `deviation` is false/true/null respectively, unless a separate current ownership violation establishes a deviation. A current `user_exception` can permit remaining work but cannot erase a known past deviation or resolve unknown history. Prior authorization does not itself grant current permission. The output echoes applicable `root_start_authorized`, or null when root work has not started. Off mode still defers current permission to host policy while preserving declared known or unknown history. Existing actual Executor ownership retains precedence; do not duplicate it.

An optional `dispatch_blocker` must be `budget`, `capability`, `authentication`, or `host_policy`. It blocks new dispatch and returns the corresponding `wait_for_<blocker>` action; capacity and dependencies remain ordinary readiness constraints. These independent constraints do not grant root fallback and are not overridden merely by a claimed root-execution exception. Existing actual Executor ownership and permitted root verification are preserved; the checkpoint does not duplicate or cancel useful work. Missing provider receipts are not a dispatch blocker.

The CLI reads one JSON object containing these readiness arguments from stdin and emits JSON. Invalid input returns a JSON error on stderr with exit status 1:

```sh
python3 /path/to/optimax/scripts/work_breakdown.py < /path/to/readiness.json
```

The host must render a visible checkpoint, invoke the helper at the required boundaries, and reconcile blockers with actual assignments/capacity before acting. The pure helper neither installs hooks nor observes tool calls, persists assignments, authenticates claimed ownership, or grants model-learning eligibility.

Prepare every controllable helper stage through the controller, dispatch with actual supported requested model and effort fields, and record attributable events in the ledger. Missing effective receipts alone do not prevent permitted dispatch; identify such work as requested-only and exclude it from model-specific learning until a genuine matching receipt and independent acceptance establish eligibility. Schema incompatibilities and known settings conflicts still block incompatible routes. Capacity, quota and dependency constraints call for queuing or replanning, not automatic root implementation; obtain an explicit user exception where required. For a late correction, preserve artifacts and useful running assignments, delegate only remaining work, and never fabricate past assignments. Opaque native workers remain unscored and optimization is partial. This applies to Advisors, Executors, reviewers, and rework. Only record an actual launch after the host confirms it; follow the controller's failure and cancellation protocol when a launch does not occur. See [controller usage](calculator.md), [policy](policy.md), and [native modes](native-modes.md).
