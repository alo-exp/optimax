HOW OPTIMAX WORKS

Use available useful slots within verified capacity. Accepted dependencies and separate ownership determine what can run together.

  1. 01

    Scope the work

    Define a bounded outcome, acceptance criteria, dependencies and exclusive write paths for each assignment. Separate independent work from tasks that must wait.

  2. 02

    Route and run together

    Select an eligible model and effort for each ready task. Run compatible tasks concurrently, count every live helper against capacity and serialize shared writes.

  3. 03

    Review, accept and learn

    The Orchestrator independently checks each result and its evidence. Accepted work unlocks successors; eligible reviewed assessments inform future routing.

BEFORE YOU BEGIN

Does Optimax take over my Orchestrator?

Your chosen session model stays in charge. Optimax recommends an Orchestrator model and effort; it does not apply that recommendation or change native settings for you.

Does it always choose the cheapest model?

No. Selection follows model and effort eligibility, task complexity, reviewed quality and policy. It does not guarantee cost savings or choose on price alone.

Does parallelization mean running everything at once?

No. Only independent ready tasks with accepted dependencies and verified capacity can run together. Shared-file and exclusive-resource conflicts stay serialized. Advisors, reviewers and rework also occupy capacity; unknown native occupancy is not an empty slot.

Can it control every native helper?

No. The host must expose the required controls and effective model settings. Opaque native helpers remain unscored, and optimization is partial when their settings or occupancy cannot be verified. Understand native mode limits.

Can I turn Optimax off?

Yes. Use $optimax off in Codex or /optimax:optimax off in Claude to stop policy dispatch, consultation and learning. The off command preserves your ledger and native controls. Read the session controls.
