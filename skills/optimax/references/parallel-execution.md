# Parallel execution

For substantial work, define a bounded work breakdown before execution. Each task identifies its intended outcome, observable acceptance criteria, dependencies, exclusive write paths and other shared resources, and Executor complexity. Decompose until independent useful work can proceed concurrently; do not create artificial fragments, duplicate work, or discard valid completed checks. Consult the appropriate Advisor before finalizing the plan or a material replan.

Every substantive phase, including Low-complexity implementation, tests, research, documentation, release preparation and rework, needs an actual bounded Executor owner. Advisor consultation is not delegated execution. Before starting, show the host assignment ID or a concrete blocker/permitted exception; planned briefs and reservations do not establish dispatch. Repeat at material phase changes, resume, late correction and before acceptance. The root may coordinate, inspect sources, run existing checks for independent verification, accept work, coordinate integration and complete authorized publication; it must not author substantive deliverables under those labels. The Orchestrator owns the plan and independently reviews each result and its evidence. A dependency is satisfied only when the Orchestrator accepts the corresponding result. A candidate marked complete, an agent's self-reported pass, or a pending review is not acceptance. Reopened work and required rework block dependent tasks until independently accepted again.

The root owns outcomes, the work breakdown, acceptance and ledger. Assign each bounded stage one execution owner: native or direct. Represent an opaque native subtree as one WBS stage; the native runtime may schedule its internal steps freely, and root acceptance of its result unlocks downstream work. Treat native stages individually as controlled only where real return, acceptance and resume boundaries exist. Do not mirror the subtree with direct assignments.

At each scheduling opportunity, form a maximal feasible ready set in plan order using only verified capacity: dependencies must be accepted, capacity available, and ownership and exclusive resources compatible with running and selected tasks. Unknown native occupancy remains unknown, not zero; do not claim maximal utilization or launch competing direct fan-out unless disjoint capacity is independently verified. Use all available useful slots; do not impose an arbitrary worker cap. Count every live helper against host capacity, including Advisors, reviewers, and rework, as well as Executors. A feasible greedy ready set is sufficient; this policy does not require a maximum-cardinality solver. Shared writes, deployments, and other exclusive resources must remain serialized.

Dispatch continuously. Recompute after accepted completion, launch failure, settled cancellation, or resource release. Start an eligible successor immediately even while unrelated slow work continues. Fill available capacity with independent ready work while reviews are pending. Respect actual host limits and user authorization; do not fabricate launch or completion records.

The host performs scheduling and native launches. The optional `scripts/work_breakdown.py` pure helper validates a snapshot through `readiness(plan, accepted, running, capacity, other_inflight=None, *, enabled=None)` and returns `ready`, `status`, and `used_capacity`. The caller must supply an independently verified nonnegative count of occupied slots outside `running`; omitted or unknown occupancy raises `ValueError`, and zero is valid only when verified. The helper does not detect occupancy. Plan tasks have `id`, `outcome`, `acceptance`, `dependencies`, `complexity` (`low`, `medium`, or `high`), `write_paths`, and `resources`. Status identifies each task's readiness or blocker; used capacity includes running tasks, other in-flight helpers, and selected ready tasks. Invalid or inconsistent snapshots raise `ValueError`. Write paths use lexical POSIX normalization, so the host must also account for actual filesystem aliases and other resource conflicts. Its greedy plan-order result describes a feasible snapshot, not an actual batch launch; it does not launch helpers, persist state, or replace independent acceptance. Recompute from current facts before acting.

All `write_paths` in one snapshot must use one POSIX namespace: project-relative paths confined to the project root, or absolute paths. Relative `.` and absolute `/` reserve their respective entire roots; normalized in-root paths such as `src/../lib` are supported. Normalized relative escapes (`..` or `../...`), NUL characters, paths beginning with two or more slashes, and mixed absolute/relative path sets raise `ValueError` before scheduling, including for running and accepted tasks and with policy off. This tightens input compatibility: callers must supply a consistent namespace instead of relying on implicit resolution. Normalization is lexical only; the helper does not consult the current working directory, resolve symlinks or filesystem aliases, or establish actual filesystem confinement.

For execution checkpoints, add optional task `execution` metadata and supply an explicit boolean `enabled` from current session status; legacy snapshots without execution metadata keep their existing behavior. Required metadata fields are `activity` and `proposed_owner`; optional fields are `assignment`, `root_started`, `root_start_authorized`, `user_exception`, and `dispatch_blocker`. Activities distinguish substantive `code`, `test_authoring`, `test_work`, `research`, `documentation`, `release_preparation`, and `semantic_integration` from root `coordination`, `source_inspection`, `independent_verification`, and `acceptance`. Describe the actual work, not a convenient label.

`capacity` and `used_capacity` count helper slots. An explicit `proposed_owner: "root"` with one of the four root activities above consumes zero helper slots when no host-returned helper assignment is present. This applies to both selected and running root tasks, including with policy off; off checkpoints still defer permission to host policy. Such tasks remain subject to accepted dependencies, write-path ownership, and exclusive resources, and they continue reserving their declared paths/resources. They may proceed with helper capacity exhausted and do not suppress an independent Executor launch. A running root task carrying any host-returned helper assignment consumes one slot, whether the role is Advisor or Executor and whether the stage is planning, design or execution. Helper occupancy and Executor execution ownership are separate facts: only an Executor at execution stage establishes the latter. Any running task with a host-returned helper also sets `preserve_existing_work: true`, including Advisors and planning/design helpers and with policy off; preserving useful work does not grant Executor ownership or change permission. A non-host-returned assignment is a proposal and does not establish helper occupancy; omitted, null or non-boolean receipt claims are not accepted substitutes for the required boolean. Legacy tasks without execution metadata, other proposed owners and substantive activities (including root exceptions) retain conservative one-slot accounting; the helper does not infer slot exemptions from missing facts. Do not include the root itself or a helper already represented by a running task in `other_inflight`; independently verify all other actual helper occupancy. Accepted assignment evidence is historical and costs no task slot; if that helper remains live elsewhere, count its actual external occupancy independently.

A returned host assignment is represented as `{"assignment_id":"ACTUAL_HOST_ID","role":"executor","stage":"execution","host_returned":true}`; an Advisor planning/design assignment does not satisfy Executor ownership. This remains a declared host snapshot, not provider authentication: compare it with the real returned host result. An exception requires concrete instruction `evidence`, `scope` equal to the exact task ID, and `authority` of `new_explicit_user_instruction` or `higher_priority_governing_instruction`; a capacity/receipt limitation is not an exception. The result adds `execution_checkpoints` per task with `execution_allowed`, `next_action`, `ownership_basis`, `provider_verified: false`, `learning_eligible: false`, `deviation`, `root_start_authorized`, and `preserve_existing_work`. With policy off, it returns `defer_to_host_policy`, never blanket root permission.

Reconcile assignment ownership with task lifecycle before scheduling. A host-returned Executor assignment at the execution stage requires the task ID in either `running` or `accepted`; a pending task with that assignment is an inconsistent snapshot and raises `ValueError`, including with policy off or nonzero `other_inflight`. Never infer that the assignment occupies an external slot or automatically add the task to `running`. Explicit running helper tasks consume one slot each (subject to the explicit root-activity exemption above), and two running tasks cannot claim the same host-returned assignment ID, regardless of activity, proposed owner, helper role or stage. Assignment metadata attached to a running task claims a current helper identity; keep historical or shared consultation context outside that current assignment field. Universal running-ID uniqueness is independent of the narrower pending lifecycle rule and does not grant Executor ownership. An accepted task may retain its assignment as historical evidence without consuming capacity or preventing independent ready work. This lifecycle consistency rule also applies to root activities carrying any host-returned helper assignment: they must be running or accepted, regardless of role/stage, policy mode or `other_inflight`. Pending root activities with returned Advisor or planning/design metadata are ambiguous and now raise `ValueError`; reconcile actual live versus historical state before calling the helper, without moving the same helper into external occupancy as a workaround. Substantive pending tasks may still carry Advisor/planning context without establishing Executor ownership; independently count any such live contextual helper outside the represented running tasks. Unreturned assignments and legacy snapshots retain their existing scheduling semantics.

The helper has no completed-but-awaiting-acceptance lifecycle state. A host must reconcile this state from actual facts before calling it; do not mark unaccepted work accepted to release capacity, retain a finished assignment as a pending current assignment, or invent occupancy. Until the host can supply a consistent supported snapshot, fail safely and reconcile externally.

Keep current permission separate from authorization when earlier root work began. If `root_started: true`, optional `root_start_authorized` accepts exactly `true`, `false`, or `null`: true declares that root work was authorized when it began, false declares it was unauthorized, and omitted/null means unknown. This is a host-declared historical fact, not provider verification; do not infer it from the current owner, current mode, a new exception, or free-text explanation. For substantive work already started, `deviation` is false/true/null respectively, unless a separate current ownership violation on a running task establishes a deviation. An accepted task’s retained Executor assignment is historical and cannot by itself create a current ownership violation; declared earlier root authorization still determines its false/true/null history. A current `user_exception` can permit remaining work but cannot erase a known past deviation or resolve unknown history. Prior authorization does not itself grant current permission. The output echoes applicable `root_start_authorized`, or null when root work has not started. Off mode still defers current permission to host policy while preserving declared known or unknown history. Existing actual Executor ownership retains precedence over root activity permission and current exceptions; do not duplicate it. For a running task with an actual Executor assignment, proposing root coordination, inspection, verification or acceptance returns `return_to_executor` with `execution_allowed: false`, rather than `root_permitted`. Represent independent root verification as a separate task with its own dependencies and resource declarations. Accepted history still returns `no_remaining_work`; off mode still returns `defer_to_host_policy`.

A running substantive root task may continue under `explicit_user_exception` only when the snapshot declares `proposed_owner: "root"`, a valid current scoped exception, `root_started: true`, and no host-returned helper assignment. A pending exception alone does not establish who owns later running work; an unexplained running task or a returned Advisor/planning helper still requires `reconcile_running_assignment`. Actual Executor ownership retains precedence. New-dispatch blockers do not stop this already-started root continuation; they still block pending dispatch. Running substantive root work retains conservative one-slot accounting, and current permission preserves the separately declared authorized/unauthorized/unknown start history. Accepted and off checkpoints retain their existing actions.

An optional `dispatch_blocker` must be `budget`, `capability`, `authentication`, or `host_policy`. It blocks new dispatch and returns the corresponding `wait_for_<blocker>` action; capacity and dependencies remain ordinary readiness constraints. These independent constraints do not grant root fallback and are not overridden merely by a claimed root-execution exception. Existing actual Executor ownership and permitted root verification are preserved; the checkpoint does not duplicate or cancel useful work. Missing provider receipts are not a dispatch blocker.

The CLI reads one JSON object containing these readiness arguments from stdin and emits JSON. Invalid input returns a JSON error on stderr with exit status 1:

```sh
python3 /path/to/optimax/scripts/work_breakdown.py < /path/to/readiness.json
```

The host must render a visible checkpoint, invoke the helper at the required boundaries, and reconcile blockers with actual assignments/capacity before acting. The pure helper neither installs hooks nor observes tool calls, persists assignments, authenticates claimed ownership, or grants model-learning eligibility.

Prepare adaptive helper stages through the controller, dispatch with actual supported requested model and effort fields, and record eligible attributable assessments in the ledger. For fixed user-directed review with policy enabled, a valid matching pre-dispatch adaptive reservation follows existing eligibility rules. Without it, or when the policy is off, use supported host dispatch and the ordinary durable review report under [the two-branch contract](calculator.md#fixed-review-and-dispatch-limits): preserve the actual host assignment ID (or no returned ID), requested settings, candidate, scope, pass and outcome. This report-only path has no controller run/epoch, never attaches a mismatched reservation or submits a score even with a later receipt, and preserves adaptive history. Unsupported fixed rungs block without substitution. Missing effective receipts alone do not prevent permitted dispatch; identify such work as requested-only. Adaptive reserved runs remain excluded from model-specific learning until a genuine matching receipt and independent acceptance establish eligibility; report-only fixed reviews remain unscored. Schema incompatibilities and known settings conflicts still block incompatible routes. Capacity, quota and dependency constraints call for queuing or replanning, not automatic root implementation; obtain an explicit user exception where required. For a late correction, preserve artifacts and useful running assignments, delegate only remaining work, and never fabricate past assignments. Opaque native workers remain unscored and optimization is partial. This applies to Advisors, Executors, reviewers, and rework. The controller's legacy `launch` event is a reservation; it does not record host dispatch confirmation, failure, or cancellation. Keep actual dispatch outcomes, including failed, uncertain, or cancelled attempts, in the ordinary durable review report or task report; unused reservations remain unused. Do not invent events, assessments, receipts, or a failure/cancellation protocol. See [controller usage](calculator.md), [policy](policy.md), and [native modes](native-modes.md).
