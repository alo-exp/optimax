# Optimax website messaging

The Circuit homepage uses the supplied Content Messaging Framework v3.0 as an editorial guide. Its core contains **14 buyer-narrative components**, followed by an SEO/GEO/AEO companion with **eight sections numbered 0–7**. Those eight sections are implementation guidance, not eight additional sequential conversion components. Applying the guide is not evidence of conversion, ranking or AI-citation improvement.

## Audience, offer and adaptation

The intended visitor already builds with Claude or Codex and understands delegation. The homepage therefore uses the guide's legitimate aware-buyer compression of components 1–4, plus the companion's product-page guidance to define the offering immediately. The exact approved H1 is **Optimize Cost, Maximize Parallel Work** and the exact subtitle is **Maximize parallelization, minimize cost**. These express the desired outcome; supporting copy explains the mechanism and qualified proof rather than claiming measured savings.

The opening names the audience and defines Optimax as an open-source plugin for delegating work. The below-fold narrative expands the practical problem, then gives mechanism → proof → benefits → objections → differentiation → offer and controls → installation → first-session guidance. The hero/navigation installation links are shortcuts for ready visitors; the complete offer and primary installation action follow the proof and objections. This is an aware-buyer product homepage, not an uncompressed 14-block sales letter. No actual customer interviews or conversion research were supplied; buyer/problem phrasing is a source-grounded editorial hypothesis.

The product must remain understandable without knowing internal roles: useful parallel work, models selected by task complexity and independently reviewed performance, and review before acceptance. The user's chosen session model keeps responsibility for decisions, review and acceptance. Use internal Orchestrator/Executor/Advisor terms only when a linked operating guide needs them.

## Claim and evidence boundaries

- Parallelization means useful, compatible ready work within verified capacity and accepted dependencies. It is not unlimited fan-out, globally optimal scheduling or an automatic speed guarantee. Advisers, review and rework consume capacity too; unknown native occupancy is not free capacity.
- The work-plan visual is explicitly illustrative, not live telemetry. Its three independent assignments have their own available inputs and separate scope/files; the review assignment concerns an already completed change. Integration waits for accepted results. No fake timings, utilization, token spend or savings appear.
- The optional readiness helper validates a supplied greedy snapshot. It does not observe occupancy, dispatch helpers or prove a global optimum. Public copy need not explain this internal helper; it must not imply those capabilities.
- Only attributable, independently reviewed results with verified effective settings can inform learned comparisons. Opaque native workers remain unscored; native optimization is partial where the host hides necessary facts.
- The chosen session model keeps control. Recommendations are not automatically applied. Installing makes the policy available and does not enable it; explicit controls govern a session. Turning it off preserves history and native settings while useful in-flight work can finish safely.
- Codex proof is limited to documented observed v0.1.0 installation, installed-skill discovery and on/off/status controls on CLI 0.166.0-alpha.6. It does not establish every client, hidden-worker control, compaction recovery or measured savings. Claude has static validation; live acceptance is pending.
- The plugin is free and MIT licensed. Host and model usage charges depend on the user's account and provider. Free software does not mean free inference.
- No customer testimonials, user totals, benchmarks, quantified savings, conversion lift, market leadership, urgency or guaranteed outcomes are supplied. Do not invent them or transfer the guide's research assertions into product proof.
- Do not publish the supplied guide, its extracted text, its private location or this internal proposal. Preserve Circuit's approved visual direction; source-level copy validation does not establish browser layout quality.

## Integration validation

The proposal and this mapping change prose only; they do not establish a new executable TDD cycle. Integration must preserve the exact hero/subtitle, command bytes, public fragments (`#how-it-works`, `#mechanism`, `#proof`, `#benefits`, `#questions`, `#install`, `#next-step`), valid source destinations and existing host controls. Meaningful assertions should check the narrative and evidence boundaries without treating arbitrary string snapshots as proof of product behavior.

The production owner must apply mandatory TDD to any changed executable behavior, then run required site tests and build against the accepted candidate. Existing root-domain/project-prefix, generated-link graph, search, clipboard, theme and accessibility contracts remain applicable. Run rendered responsive and interactive acceptance when the authorized browser is available, and report it separately from DOM/source checks and live host acceptance. Do not describe this new Circuit candidate as browser verified on the strength of an earlier site's HTTP or DOM checks.
